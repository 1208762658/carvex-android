# 导航消息映射到仪表 — 可行性分析

分支：`research/nav-cluster-mapping`（自 `v15-ready-gate` @ `4d25a45` 拉出，46 commits，工作树干净）
适用对象：VW MIB3 866F（蓝牙 `VW BT 5384`）· CarVeX 手机侧（iPhone 角色）

---

## 一、结论先行

| 层 | 结论 | 依据强度 |
|---|---|---|
| 协议通道（iAP2 导航，特性 17） | **可行，而且 866F 真的订阅了**：它声明收 `5201/5202`，并在会话里主动发 `5200 componentList=[1]` | 实车日志，强 |
| 数据源（导航内容） | **极薄**：全仓库只有一处把 CarWith HUD 的 2 个字段（路名、剩余距离）塞进 `5201`；且该入口**从未被触发**（实测 3091 行日志里 `carlife_show_hud_info` 0 次） | 代码+日志，强 |
| 仪表显示 | **不由 CarVeX 决定，当前条件下不可实现**：仪表由 866F 固件渲染，App 无通道；866F 未声明收 `5204`；原厂口径 CarPlay 与内部导航互斥、仪表只列媒体/电话模式 | 代码事实+官方手册，中（缺 866F 固件级证据） |

一句话：**"发导航数据给 866F"可以做，"导航上仪表"目前做不到；且现在连第一条真数据都没发出去（订阅状态从没置位）。**

## 三、代码现状（三条硬事实）

1. **订阅没落库 → 后续发送闸门永远是关的**
   - `5200` 在会话期实际由 `AirSession.kt:259` 拦截，只回空 `5201`，**没有调用 `NavigationGuidance.start()`**，所以 `NavigationGuidance.active` 一直是 `false`。
   - 而 `SessionController.kt:256-264`（`deliverNavigation`）和 `AirSession.kt:1192`（`navigationRouteUpdate`）都以 `active` 为前置条件 → **即使 CarWith 推 HUD，也一条 `5201` 都发不出去**。
   - 另一条路径 `Bootstrap.kt:1064-1077` 的 `0x5200` 处理确实会 `start()`，但它属于会话内分发器；实测 `5200` 只出现在 `CONTROL_READY` 探测批次里，从未在业务阶段再来一次。
2. **数据映射只有两个字段**
   - `SessionController.kt:355-368`：`carlife_show_hud_info` → 只取 `road_name`（→ `currentRoad`）与 `remain_distance`（→ `distanceRemaining`）。
   - `action`、`navi_turn`、`total_distance` 只写进诊断串 `hostHud`，**没有映射**（代码注释明确"未确认的机动/车道枚举不主动伪造"）。
3. **编码器齐全但出站只用过 5201，且是空包**
   - `NavigationGuidance.kt:95-124` 已实现 `5201`（26 个参数，含 ETA/剩余时间/到机动点距离/机动表/车道摘要/红绿灯后电量）、`5202`（13 个参数，含转向类型、动作后的路名、出口信息）、`5204`（车道组）。
   - `navigationManeuverUpdate()` / `navigationLaneUpdate()` **全仓库无调用点**。

## 四、为什么"到仪表"不归我们管

1. **角色决定权限。** CarVeX 是手机侧（iPhone 角色），对车的唯一上行通道就是 iAP2 `5201/5202`。仪表（组合仪表）的显示内容由 866F 固件自己渲染，经车内私有链路（CAN/LVDS）下发；App 侧没有任何写仪表的接口。
2. **866F 只收 `5201/5202`，不收 `5204`。** 即使我能拿到车道级数据，866F 也不会消费；伪造车道消息属于"发进未知路径"，按仓库约定不做。
3. **原厂口径是互斥的。** 上汽大众《导航操作手册》："内部导航和 Apple CarPlay 导航不可同时使用，新开启的导航会替代之前开启的导航"；同一份手册讲 CarPlay 场景时只写"**组合仪表的显示屏上显示媒体运行模式和电话运行模式**"，没有导航运行模式。
4. **现实的旁证。** 三代 866A/866F 主机想"仪表显示 CarPlay"，公开解法是换一块能直连 CarPlay 的第三方仪表（抖音已见成品方案），即**原厂仪表这条路本身就不通**。

> 反过来说：866F 主动发 `5200` 说明它的特性 17 是活的（可能在车机屏导航卡片、限速/罗盘、或给仪表的引导数据里用）。**到底渲染到哪里，只能上车实测，固件里没有直接证据**——这正好是 `research/.../09-runtime-evidence.md §9.3` 记的 `OPEN-NAV-2`。

## 五、能做的事：三级实施 + 一个判定实验

### P0 订阅置位（必做，改动 1 个文件，风险低）
- 在 `AirSession.kt` 的 `0x5200` 分支里：`NavigationGuidance.start(command.fields)`；解析失败才降级为"空 `5201` + 日志"，解析成功则记录 `components/mask`，`active=true`。
- 首个 `5201` 保持空载荷（已有成功样本，不改行为），后续才发真实数据——避免把握手期弄脏。
- 诊断日志：`navigation start components=[1] mask=0`，用于确认订阅在业务阶段是否再次出现。

### P1 数据映射补全（把"导航消息"变成真的导航消息）
- `5201`：`currentRoad`←`road_name`；`distanceRemaining`←`remain_distance`；`distanceToManeuver`← CarLife HUD 的转向距离；`timeRemaining`/`eta`← 若宿主给得出；`destination` 视字段而定。
- `5202`：`index`、`type`←`navi_turn`（枚举待闭合，见 P2）、`afterRoad`←路名、`distance`←到机动点距离。
- 只在 `5200` 订阅有效时发送，沿用 `r.own` 资源模型，不新开线程（稳定性优先）。

### P2 枚举闭合（唯一真正的不确定性）
- `OPEN-NAV-4`：固件 `maneuver type` 类型号 → 语义的映射未读完；CarLife `navi_turn` 枚举也没抓到真值。
- 做法：固定路况下逐个试 `type`（1..N）+ 一条 `5202`，看车机屏/仪表反应；同时抓一次真 iPhone 跑高德时的 `5202` 原始字节对照（iPhone 侧抓包是唯一权威口径）。
- 在枚举闭合前，宁可只发 `5201`（路名+距离，语义确定），也不猜 `5202` 的转向箭头。

### P3 数据源接入（CarWith 没给就换源）
- 现状：`carlife_show_hud_info` 实测 0 次。可能是当次没开导航，也可能 CarWith 不给这个 action。
- 验证：手机上开高德导航并投到 CarWith，看日志是否出现该 action 及 extras 全集（`action/navi_turn/remain_distance/total_distance/road_name`）。
- 兜底：`NotificationListener` 解析高德/百度导航通知（需通知使用权；字段粗糙、限速/车道拿不到；稳定性风险高，仅在 CarWith 通道确认不存在时启用）。

### 判定实验（决定"仪表"这一问的最终答案）
1. 打一个诊断包：P0 + P1（先只发 `5201`，`5202` 用一组固定 type）。
2. 车上：进 CarPlay → 手机开导航 → 会话需稳定越过 `CONTROL_READY+7.5s` 窗口。
3. 观察三点：车机屏 CarPlay 地图卡片是否出现"路名+剩余距离"；仪表"导航/行驶信息"页是否出现箭头；866F 是否回 `5203` 或再发 `5200`。
4. 判定：**仪表出箭头 → 866F 固件确实把 iAP2 导航接进了仪表，功能可实现（补 P1/P2 即可）；仪表无任何变化 → 当前条件下不可实现，只能走第三方仪表或放弃。**

## 六、风险与不做的事

- 不伪造 `5204`（866F 未声明接收）；不猜 `5202` 转向枚举（发错会被固件"整条拒绝、不回应、不改状态"，无副作用但也无收益）。
- `active=true` 后 `deliverNavigation` 的 IO 并发要挂在会话资源上，避免 teardown 竞争（`r.own`）。
- 导航语音播报不走 iAP2：866F 只认一条 main 音频（`docs/866F-声音分流-不支持原因分析.md` R1/R3），导航播报交给 CarWith 自己的音频通路。
- 当前会话稳定性仍是前置条件（自动进 CarPlay 页、`5200` 只出现一次），导航功能不能反过来拖握手。
