# 导航消息映射到仪表 — 可行性分析

分支：`research/nav-cluster-mapping`（自 `v15-ready-gate` @ `4d25a45` 拉出，46 commits，工作树干净）
适用对象：VW MIB3 866F（蓝牙 `VW BT 5384`）· CarVeX 手机侧（iPhone 角色）

---

## 一、结论先行

| 层 | 结论 | 依据强度 |
|---|---|---|
| 协议通道（iAP2 导航，特性 17） | **可行，而且 866F 真的订阅了**：它声明收 `5201/5202`，并在会话里主动发 `5200 componentList=[1]` | 实车日志，强 |
| 数据源（导航内容） | **极薄**：全仓库只有一处把 CarWith HUD 的 2 个字段（路名、剩余距离）塞进 `5201`；且该入口**从未被触发**（实测 3091 行日志里 `carlife_show_hud_info` 0 次） | 代码+日志，强 |
| 仪表显示 | **可实现**：原车 + 真 iPhone 实测，组合仪表能显示转向箭头、道路名与剩余距离 → 866F 固件确实把 iAP2 导航数据（`5201/5202`）渲染到仪表，我们只要喂对字段与枚举 | 用户实车观察，强（先前"官方手册只列媒体/电话"的判断据此作废） |

一句话：**功能可实现，且仪表是 866F 自己渲染的——我们的任务只有两件：把订阅状态真正置位、把 `5201/5202` 的字段与转向枚举喂对。当前连第一条真数据都还没发出去。**

> 结论修订记录：初版依据上汽大众《导航操作手册》"CarPlay 下组合仪表显示媒体/电话运行模式"推断仪表不显示导航。该推断被真车实测推翻——手册描述的是**内建导航**的仪表模式，CarPlay 导航走的是 iAP2 特性 17 的独立通道，866F 会自行把它送进仪表。原判断作废，保留在此仅作审计。

## 三、代码现状（三条硬事实）

1. **订阅没落库 → 后续发送闸门永远是关的**
   - `5200` 在会话期实际由 `AirSession.kt:259` 拦截，只回空 `5201`，**没有调用 `NavigationGuidance.start()`**，所以 `NavigationGuidance.active` 一直是 `false`。
   - 而 `SessionController.kt:256-264`（`deliverNavigation`）和 `AirSession.kt:1192`（`navigationRouteUpdate`）都以 `active` 为前置条件 → **即使 CarWith 推 HUD，也一条 `5201` 都发不出去**。
   - 另一条路径 `Bootstrap.kt:1064-1077` 的 `0x5200` 处理确实会 `start()`，但它属于会话内分发器；实测 `5200` 只出现在 `CONTROL_READY` 探测批次里，从未在业务阶段再来一次。
2. **数据映射只有两个字段**
   - `SessionController.kt:355-368`：`carlife_show_hud_info` → 只取 `road_name`（→ `currentRoad`）与 `remain_distance`（→ `distanceRemaining`）。
   - `action`、`navi_turn`、`total_distance` 只写进诊断串 `hostHud`，**没有映射**（代码注释明确"未确认的机动/车道枚举不主动伪造"）。
3. **编码器齐全但出站只用过 5201，且是空包**
   - `NavigationGuidance.kt:95-124` 已实现 `5201`（26 个参数，含 ETA/剩余时间/到机动点距离/机动表/车道摘要/红绿灯后电量）、`5202`（13 个参数，含转向类型、动作后的路名、出口信息）、`5204`（车道组）。
   - `navigationManeuverUpdate()` / `navigationLaneUpdate()` **全仓库无调用点**。

## 四、仪表这一环已经通了，剩下的是"喂对数据"

1. **显示方是 866F，不是我们。** CarVeX 是手机侧（iPhone 角色），唯一上行通道是 iAP2 `5201/5202`；仪表屏幕由 866F 固件按这两个消息渲染，经车内私有链路（CAN/LVDS）下发。
2. **真机已证这条路存在。** 原车 + 真 iPhone 导航时，仪表能出转向箭头、道路名、剩余距离 → 866F 固件确实消费 iAP2 导航数据，不是靠内建导航。既然真机能显示，我们发同样的数据同样能显示。
3. **866F 只收 `5201/5202`，不收 `5204`。** 车道级指引（`5204`）它压根没声明接收，不做、也不伪造。
4. **因此风景点从"能不能"变成"准不准"**：`5202` 的转向类型（箭头形状）、距离单位、剩余距离文本、以及"什么时候开始发"，都必须和真机一致，否则仪表会显示错箭头或干脆不显示。

### 4.1 仪表最小可显示字段集（据真机现象 + 固件字段表反推）

| 仪表元素 | 来源消息 | 参数 |
|---|---|---|
| 转向箭头 | `5202` | `type`（关键，枚举待标定）、`drivingSide`、`junctionType`（环岛/分岔用） |
| 动作后的道路名 | `5202`（引导中）/`5201` | `afterRoad` / `currentRoad` |
| 剩余距离 | `5201` | `distanceRemaining` + `distanceDisplay` + `distanceUnits`（三者都给，避免仪表只认文本或只认数值） |
| 到机动点距离 | `5202` + `5201` | `distance` / `distanceToManeuver` (+ `…Display` / `…Units`) |
| 机动点索引 | `5201` | `maneuverList`（重复 u16，指向 `5202` 的 `index`）、`maneuverCount` |
| 引导状态 | `5201` | `state`（引导中/结束）、`beingShown`（是否正在显示） |

> 结论：**只发 `5201` 不出箭头**（箭头在 `5202`）；只发 `5202` 不出发距离/路名。两条必须配对：先 `5201` 给机动表，再 `5202` 按 `index` 喂每一个机动点。

### 4.2 剩余的三个不确定点
- `OPEN-NAV-4`：`maneuver type` 数值 → 箭头语义未闭合（固件 `keyForType` 只给了键名映射，没给数值枚举）。
- 距离单位枚举（`distanceUnits`）未闭合——用 `distanceDisplay` 文本兜底可绕过。
- 首个合法发送时机：必须在 `5200` 订阅之后、会话跨过 `CONTROL_READY+7.5s` 窗口，太早发会被固件"整条拒绝、不回应、不改状态"。

## 五、能做的事：三级实施 + 标定与验收

### P0 订阅置位（必做，改动 1 个文件，风险低）
- 在 `AirSession.kt` 的 `0x5200` 分支里：`NavigationGuidance.start(command.fields)`；解析失败才降级为"空 `5201` + 日志"，解析成功则记录 `components/mask`，`active=true`。
- 首个 `5201` 保持空载荷（已有成功样本，不改行为），后续才发真实数据——避免把握手期弄脏。
- 诊断日志：`navigation start components=[1] mask=0`，用于确认订阅在业务阶段是否再次出现。

### P1 数据映射补全（把"导航消息"变成真的导航消息）
- `5201`：`currentRoad`←`road_name`；`distanceRemaining`←`remain_distance`；`distanceToManeuver`← CarLife HUD 的转向距离；`timeRemaining`/`eta`← 若宿主给得出；`destination` 视字段而定；**必须补 `maneuverList`（指向下面 5202 的 index）和 `beingShown`**。
- `5202`：`index`（与 `maneuverList` 对齐）、`type`←`navi_turn`（经 P2 标定翻译）、`afterRoad`←道路名、`distance`←到机动点距离（同时给 `distanceDisplay` 文本兜底单位枚举）。
- 只在 `5200` 订阅有效时发送，沿用 `r.own` 资源模型，不新开线程（稳定性优先）。

### P2 转向枚举标定（唯一真正的不确定性）
- `OPEN-NAV-4`：固件 `maneuver type` 数值 → 箭头语义没有闭合；CarLife `navi_turn` 枚举也没抓到真值。
- **标定法（一次会话内可完成）**：调试开关进入"标定模式"，每按一次方向盘键/屏幕按钮就把 `type` 递增 1 并发一条 `5202`（`index=0`、`distance=200m`、`afterRoad="标定"`），人在仪表上看到箭头形状后记一行。目标集合只需覆盖实际会遇到的 10 类：直行、左转、右转、左并线、右并线、左掉头、环岛入口、环岛出口、分岔左右、到达终点。一轮标定即可得到 `type → 箭头` 表，写进代码常量。
- 优先级：先标定这 10 类，其余留给后续；标不出来的值一律不发（宁可不显示箭头，也不显示错箭头）。

### P3 数据源接入（CarWith 没给就换源）
- 现状：`carlife_show_hud_info` 实测 0 次。可能是当次没开导航，也可能 CarWith 不给这个 action。
- 验证：手机上开高德导航并投到 CarWith，看日志是否出现该 action 及 extras 全集（`action/navi_turn/remain_distance/total_distance/road_name`）。
- 兜底：`NotificationListener` 解析高德/百度导航通知（需通知使用权；字段粗糙、限速/车道拿不到；稳定性风险高，仅在 CarWith 通道确认不存在时启用）。

### 验收实验（现在判的是"准不准"，不是"能不能"）
1. 打诊断包：P0 + P1 + P2 标定模式（`5201` 带路名/剩余距离/机动表，`5202` 带当前机动的 type 与距离）。
2. 车上：进 CarPlay → 手机开导航 → 会话越过 `CONTROL_READY+7.5s`。
3. 验收标准：**仪表出现与手机导航一致的箭头、路名、剩余距离，且转向 200m/100m/50m 三档刷新正常**；车机屏 CarPlay 地图卡片同步显示同一组信息。
4. 失败分支：有路名/距离但无箭头 → `5202` 未配对成功（查 `index`/`maneuverList`）；箭头错位 → 枚举标定错；全无 → `5200` 订阅仍未置位。

## 六、风险与不做的事

- **只做标定，不凭空猜**：`type` 枚举用车上标定得到，未标出的值一律不发；不伪造 `5204`（866F 未声明接收）。
- **配对顺序**：`5201` 的 `maneuverList` 必须先于 `5202` 的 `index` 到位，否则仪表拿不到箭头所指的机动点。
- `active=true` 后 `deliverNavigation` 的 IO 并发要挂在会话资源上，避免 teardown 竞争（`r.own`）。
- 导航语音播报不走 iAP2：866F 只认一条 main 音频（`docs/866F-声音分流-不支持原因分析.md` R1/R3），导航播报交给 CarWith 自己的音频通路。
- 当前会话稳定性仍是前置条件（自动进 CarPlay 页、`5200` 只出现一次），导航功能不能反过来拖握手；发送窗口在视频稳定后，不要抢在激活期。
