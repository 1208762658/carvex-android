# 866F 声音分流：为什么现在不支持

> 分支：`research/866f-audio-split`（基于 `v15-ready-gate` / `4d25a45 v45`）
> 车机：大众 MIB3 866F（H39 / 6095，BT `VW BT 5384`）
> 手机：Xiaomi 25102RKBEC / Android 17，CarVeX `com.baidu.carlife.xiaomi`
> 本文只做证据整理与结论，不含生产改动。

---

## 0. 一句话结论

**"不支持分流"不是某一个 bug，而是三层同时不成立：**

1. **车机层（硬限制）**：866F 的 `appconnectd` 只接受**一条手机主动发起的音频通道**。第二条 SETUP 会挂起约 2 秒，然后回 `400`，并在**同一毫秒**关掉 RTSP（v14.6 alert / v14.11 speech 两次实测同构）。
2. **协议/时序层**：866F 在 `CONTROL_READY + ~7.5s` 关闭 RTSP（会话激活超时）。第二条通道的 SETUP 往返就要 2s，抢不进这个窗口；v14.11 实测反而把 EOF 从 `+7.5s` 提前到 `+2.97s`。
3. **实现层**：CarVeX 的音频模型本身就是"一条主音频 + 单一 owner"（`MainAudioOwnership` 把 category 1 和 3 都算 main audio），生命周期 gate 又以 `type` 为键、`TEARDOWN` 只带 `type`，所以**既不能两条 main 并存，也不能中途只拆一路换通道**。

要让分流成立，缺的不是"再写一段代码"，而是**三条证据**（见 §5）：866F `/info` 的完整 audio 条目、真 iPhone 在同车机上的双流基线、866F 是否会经 iAP2 主动请求 alert/speech。这三条现在都是缺的。

---

## 1. 先把"分流"这个词拆开

这条链路里"分流"至少有三层含义，混在一起讨论就会得出错误结论：

| 层 | 含义 | 现在状态 |
|---|---|---|
| L1 传输/协议 | 媒体音、导航播报、提示音各走**一条独立 CarPlay 音频流**（`type` 100/101/102 + `audioType` media/default/alert/speechRecognition） | **只有 media 一条成立** |
| L2 宿主分类 | CarWith 的 CarLife mixing 宿主把 PCM 按 `category=1/2/3` 分开回调给 CarVeX | **宿主给了三路，CarVeX 只有一路能落地** |
| L3 车内输出 | 车机把这几种声音送到不同物理输出/独立音量通道 | **CarPlay 不提供这个语义**：接收端是混音，不是给你的手机两个输出 |

所以真正能讨论的只有 L1+L2：**手机侧分开送、车机侧分开接**。L3 不在协议能力范围内。

## 2. 现状链路（代码事实）

```
CarWith (小米车联) / CarLife 引擎
  └ ISystemAudioCallback.onAudioStreamReady(pcm, category=1..3, ...)   ← 宿主侧分类
        │  VendorCastHost.systemAudio（校验 category ∈ 1..3）
        ▼
  HostAudioBridge.receive(pcm, category, format)                      ← 三条独立 lane（各 8 槽队列）
        │  queues = (1..3).associateWith{Channel<Block>(8)}
        ▼
  SessionController.requestAudio(category) → AudioDemandGate
        ▼
  AirSession.createAudio(category)                                    ← 一个 category 一次 SETUP
        │  CarPlayAudioPlan.routeForCategory:
        │    1 → type102/media（回退 type100/media）
        │    2 → type100/alert（回退 type101/default）
        │    3 → type100/speechRecognition
        ▼
  866F appconnectd  ← 只接受 1 条手机主动发起的音频流
```

关键落点：

- `host-carlife-mixing/.../vendor/VendorCastHost.kt`：`onAudioStreamReady` 校验 `category !in 1..3` 直接丢；`onAudioStateChange` 亦然。**宿主侧确实分了三类。**
- `core/.../sessioncore/HostAudioBridge.kt:47`：`queues=(1..3)`，每类一条 lane，互不阻塞；`attach()` 允许"合并已建立的类别"，并明确"附加 alternate 不得关闭 main"。
- `core/.../sessioncore/MainAudioOwnership.kt:88`：`Categories 1 and 3 send only while we hold main audio` —— **category 1 和 3 共用同一份 main audio 所有权**。
- `protocol-carplay/.../core/CarPlayAudioPlan.kt:155`：`bootstrapPlayback(...) = listOf(1).mapNotNull{...}` —— 预建**只有** category 1。
- `bridge/.../SessionController.kt:541`：866F 上 speech（category 3）**主动 SETUP 被代码显式抑制**；`:1062` 仍保留 `startSpeech` 入口，但走不到 SETUP。
- `protocol-carplay/.../core/AudioStreamLifecycle.kt`：lease 键是 `(type, purpose)`，`TEARDOWN` 只带 `type`，"一个 type 上未确认的 teardown 会毒化该 type 到重连"。

**也就是说：宿主给了 3 路，代码结构允许 3 路，但最后只有 1 路能过车机。** 这是现象，不是根因。

## 3. 五条根因（按"能不能改代码绕过"排序）

### R1 固件只接受一条手机主动音频流 —— 不可用代码绕过

实测（两次独立复现，同一模式）：

| 版本 | 第一条 | 第二条 | 结果 |
|---|---|---|---|
| v14.6 | media（未发）| `type100/alert`（cat 2）| 挂起 → `400` 与 RTSP `EOF` **同一毫秒**；`EOF = CONTROL_READY+7.5s` |
| v14.11 | `type102/media` SETUP **200**，AAC RTP 正常 | `speechRecognition`（cat 3，cseq=48）| 挂起 **2.011s** → `400` 与 `EOF` **同一毫秒**；`EOF` 提前到 `+2.97s` |

代码里已把这个结论写成注释与策略：

- `CarPlayAudioPlan.kt:148-154`：`H39/6095 accepts exactly ONE phone-initiated audio channel (media); speech/alert must be demand-driven`
- `SessionController.kt:541-545`：`never actively SETUP a speech (category 3) stream ... hang ~2s -> 400 -> EOF ... kills the whole RTSP session`

判定：**在 866F 上"两条并存"这条路，已经被实车打死两次。** 不是参数问题、不是编码问题、不是时序微调能救的——v14.10 禁 alert、v14.11 只建 media 都是这条的直接后果。

### R2 会话激活窗口只有 ~7.5s（先把时间花在哪就决定生死）

- 866F 在 `CONTROL_READY + ~7.5s` 关 RTSP（`21/25device-log` 多次同值）。
- v14.8 起把 splash 6s → 1.5s，就是为了让音频 SETUP 落在窗口内；v14.11 只建 media 后窗口反而缩到 `+2.97s`。
- 结论：**第二条通道的 2s 挂起本身就在吃窗口**。哪怕车机肯接受，也得先解决"激活到底等什么"（`0x5200→5201` 闸门假设已在 v14.5 被证伪，`0x4300`、蓝牙层 `4e0b` 在 v14.6/v14.7 也被证伪），**音频分流排在激活问题之后**。

### R3 架构上"主音频只有一个 owner"，1 和 3 天然互斥

`MainAudioOwnership` 的设计前提写得很直白：

> 发送 main audio 时如果车机也持有该流，会听到两条 main 重叠、电平跳动，而日志上看不出异常。

于是：

- `takeOwn()` 在 `THEIRS` 状态下**直接抛异常**，抑制新的 main SETUP；
- `allowsMainSend()` 只有 `OURS` 才放行；
- 866F 对 mid-session 的 release 公告**直接 RST**（`releaseOwnSilent()` 注释，`90(1) 2ca997d3/cf22ea8c`）。

**category 3（语音）被当作 main audio 的第二个使用者，而不是"另一条独立通道"。** 这跟 R1 的固件行为是对齐的：车机也只认一条 main。

### R4 生命周期 gate 以 type 为键，`TEARDOWN` 只带 type —— 不能热切换、不能只拆一路

`AudioStreamLifecycle.reserve(type, purpose, id)`：同一 `(type,purpose)` 只能有一个 lease；关闭走 `beginClose` → `TEARDOWN(streams=[{type}])`，**未确认就保留 tombstone，该 type 在本会话内不可再用**。

后果：
- 想"媒体走 type102、播报走 type100"要先拆一条再建一条，而 `TEARDOWN` 只带 type，等于把同 type 的所有用途一起拆；
- 一旦 teardown 没被确认（EOF 场景极常见），这个 type 直接废掉，只能重连；
- 所以**动态换路（分流→合流→再分流）在当前生命周期模型里不成立**，不是加个分支就行。

### R5 宿主桥没有分流入口：只保留默认 PCM 路由，CarLife 的音频通道没接

- `VendorCastHost.selectCarLifePlusAudio()` 实现只有一行事件：`audio-route-default-pcm`。README 明确：**"不主动发送蓝牙音频路由请求"，"后续若接入音频路由协商，应根据已协商的通道和宿主回复实现"**。
- `CarVeX-本地劫持方案.md` 的"未做"清单里写着：**音频（9240/9241）仍走 CarVeX 自己的音频通道，没接 CarLife 的 PCM**。
- 也就是说：想让"导航播报走 CarWith 原生蓝牙通道、媒体走 CarPlay"这种**跨链路分流**，桥里根本没接线；现在所有声音都从 CarLife 引擎的 PCM 出来，被 CarVeX 压进同一条 media 流。

### R6 证据缺口（决定了"到底能不能分流"还没定案）

| 缺口 | 为什么关键 |
|---|---|
| 866F `/info` 的 `audioFormats` 原文没保存 | 不知道它到底广告了哪些 `streamType` / `audioType` 的 **output mask**。若只广告 `102/media`，那除媒体外**没有任何可分流目标**；若广告了 `101/default`，才谈得上第二路 |
| 真 iPhone 在同一台 866F 上的基线抓包 | 只有它能区分"866F 硬限制"与"我们少做了 capability 声明/请求" |
| 866F 是否经 iAP2 主动请求 alert/speech | 代码注释给的假设是"iPhone carkitd 从不自己开 alert，车机经 iAP2 请求后才建"。866F 从不请求 → "按需建"这条路在本车机上等于不存在 |

（`AMCar-清单-866F.md` 第 5/6 项也把 iPhone 侧 `/info` 原文、SDP 原始记录列为缺口。）

### R7 协议语义：CarPlay 的分流是"接收端混音"，不是"两路物理输出"

`carvex-carplay-research/research/protocol/airplay_audio_mic_channel` 已定案的两条约束，直接否掉了两个常见方案：

- `R-1.6`：**没有证据表明导航提示音走独立流、独立 raw 或与媒体混音** —— 不得假设。
- `R-5.4`：**拿到"媒体音+导航提示音同时存在"的抓包前，不得实现自动压低媒体音并声称符合车机预期；不得把提示音强行混进媒体流**（会破坏 PT/时间戳统计）。

所以"我在手机侧混音/闪避，就当分流做完了"这条路，在现有证据规则下只能算**本端实验策略**，不能宣称兼容。

## 4. 为什么"再写一段代码"解决不了

把上面串起来看：

```
分流需要 ≥2 条并存音频流
  ├ 866F 只接受 1 条（R1）              ← 硬限制，绕不过
  ├ 激活窗口 7.5s，第二条要 2s（R2）      ← 时序上先输
  ├ main audio 单 owner，1/3 互斥（R3）   ← 架构前提与车机行为一致
  ├ type 级 teardown，不能热切换（R4）    ← 换路=拆整 type
  └ 宿主侧只有默认 PCM 路由（R5）         ← 跨链路分流没接线
```

任何"加一个 category 分支"的改法，都会在 R1 处被 400+EOF 打断；任何"拆一条建一条"的改法，会撞上 R4 的 type tombstone；任何"我自己混音"的改法，会被 R7 的证据规则挡在"实验"这一层。

## 5. 下一步实验（按性价比排序，都不改生产代码）

| # | 实验 | 需要的材料 | 判据 | 成本 |
|---|---|---|---|---|
| E1 | **真 iPhone 基线**：同一台 866F，导航播报 + 音乐同时出声，抓 RTSP + `/info` | iPhone、btsnoop/RTSP 抓包 | 若 iPhone 也只有 1 条 SETUP → **R1 是硬限制，结案**；若有 2 条（含 `101/default`）→ 我们缺的是能力声明/请求，可以继续 | 中（要一台 iPhone + 抓包） |
| E2 | **保存 866F `/info` 的 audio 条目**：现在 `AudioCapabilities` 已打 `INFO audio #N streamType=... audioType=... outputMask=...`，只是没留全文 | 一次完整会话日志 | 拿到 output mask 才知道"第二路有没有目标可建" | 低（只改日志留存） |
| E3 | **`type101/default`(alternate) 单条试探**：先不建 media，只建 alternate，看 200 还是 400 | 现成代码，加一个只在研究分支用的开关 | 200 → 说明"一条"限制与 type 无关，alternate 可用；400 → 866F 只认 `102/media` | 低 |
| E4 | **车机请求路径观测**：记录 866F 是否发过任何音频相关 iAP2 请求（alert/speech） | 现有 `RuntimeIap` 已能收，补日志 | 从没请求 → "按需建"在本车机不存在 | 低 |
| E5 | **本地混音 + ducking**（仅实验）：CarVeX 侧把 cat3 混进 cat1 并压低媒体 | 纯本地 | 能听到"播报时音乐变轻"，但车机侧仍是一路 | 低，但按 R7 不得宣称兼容 |

**建议顺序：E2 → E1 → E4 → E3 → E5。** E2 最便宜，且直接决定后面还有没有得试；E1 是唯一能给"硬限制"定案的实验。

## 6. 三条候选路线（含代价）

| 路线 | 做法 | 前置 | 代价 |
|---|---|---|---|
| A 等车机请求 | 只在 866F 主动请求时建第二条（alert/speech） | E4 证明它会请求 | 若它从不请求 → 路线作废（当前证据倾向作废） |
| B 单条 + 换路 | 播报时拆 media、建 speech，播报完再切回 | E3 证明存在可用的第二 type；R4 的 teardown 要能只拆该 type | 每次播报一次 SETUP/TEARDOWN，切换有静默 gap；teardown 未确认会废 type |
| C 本地混音 | CarVeX 侧混音/ducking，车机始终只收一路 | 无 | **不是真分流**：车机只有一个音量、无法单独导航音量；按 R7 只能算实验 |
| D 接 CarLife 音频通道 | 音频改走 CarWith 自己的 9240/9241，让 CarLife 引擎决定分流 | 桥要接 audio route 协商（`selectCarLifePlusAudio` 目前是空的） | 改动面大；但这是唯一可能让"导航/媒体在车机侧分开"的路径（因为分流由 CarLife/车机侧决定，不走 CarPlay） |

**当前建议：先不选路线，先把 E2/E1 的证据补齐。** 在拿到 866F `/info` 的 audio 条目与真 iPhone 基线之前，任何分流实现都是在猜。
