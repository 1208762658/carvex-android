# 866F 声音分流：为什么现在不支持

> 分支：`research/866f-audio-split`（基于 `v15-ready-gate` / `4d25a45 v45`）
> 车机：大众 MIB3 866F（H39 / 6095，BT `VW BT 5384`）
> 手机：Xiaomi 25102RKBEC / Android 17，CarVeX `com.baidu.carlife.xiaomi`
> 本文只做证据整理与结论，不含生产改动。

---

## 0. 一句话结论

**"不支持分流"不是车机不行，而是我们没走到车机允许的那一步。** 真 iPhone 在同一台 866F 上已经证明：媒体、导航、通话能用方向盘按键**分别调音量** —— 这就是车机对**多条音频流按 `audioType` 独立增益**的直接证据。我们要补的是三件事：

1. **会话必须先真正激活并活着**（这是第一前置，不是并行项）：我们两次第二条 SETUP 的 `400` 都与 RTSP `EOF` 同一毫秒，而会话当时本就因为激活超时（`+7.5s` / `+2.97s`）在被拆。真 iPhone 的会话是活的，所以它能建第二条。
2. **路由与能力声明要跟车机对得上**：导航提示音在 CarPlay 里是 **AltAudio**（`type101` + `audioType=default`），我们却把 category 2 先映射到 `type100/alert`；如果 866F 只广告 alt 路由，`selectPlayback` 在 `/info` 阶段就把候选筛空，**连试都没试过**。
3. **实现模型要允许两条并存**：`MainAudioOwnership` 把 category 1/3 都当 main audio、只认一个 owner；`AudioStreamLifecycle` 以 `type` 为键、`TEARDOWN` 只带 `type`。路由修好之后，这两处仍是硬墙。

结论：**分流可实现**，卡点是"激活 → 路由/声明 → 单 owner 模型"这三段，而不是"固件不让"。

## 1. 先把"分流"这个词拆开

这条链路里"分流"至少有三层含义，混在一起讨论就会得出错误结论：

| 层 | 含义 | 现在状态 |
|---|---|---|
| L1 传输/协议 | 媒体音、导航播报、提示音各走**一条独立 CarPlay 音频流**（`type` 100/101/102 + `audioType` media/default/alert/speechRecognition） | **车机支持（真 iPhone 已证实）**；我们只建了一条 media |
| L2 宿主分类 | CarWith 的 CarLife mixing 宿主把 PCM 按 `category=1/2/3` 分开回调给 CarVeX | **宿主给了三路，CarVeX 只有一路能落地** |
| L3 车内输出 | 车机按 `audioType` 给每一路独立增益（方向盘按键分别调媒体/导航/通话音量） | **不在"手机侧"能力范围内**：由车机实现，我们只要把流分对，音量分离是车机的事 |

所以真正能讨论的只有 L1+L2：**手机侧分开送、车机侧分开接**。L3 不在协议能力范围内。

## 2. 现状链路（代码事实）

```
CarWith (小米车联) / CarLife 引擎
  └ ISystemAudioCallback.onAudioStreamReady(pcm, category=1..3, ...)   ← 宿主侧分类
        │  VendorCastHost.systemAudio（校验 category ∈ 1..3）
        ▼
  HostAudioBridge.receive(pcm, category, format)                      ← 三条独立 lane（各 8 槽队列）
        │  queues = (1..3).associateWith{Channel<Block>(8)}
        ▼
  SessionController.requestAudio(category) → AudioDemandGate
        ▼
  AirSession.createAudio(category)                                    ← 一个 category 一次 SETUP
        │  CarPlayAudioPlan.routeForCategory:
        │    1 → type102/media（回退 type100/media）
        │    2 → type100/alert（回退 type101/default）
        │    3 → type100/speechRecognition
        ▼
  866F appconnectd  ← 只接受 1 条手机主动发起的音频流
```

关键落点：

- `host-carlife-mixing/.../vendor/VendorCastHost.kt`：`onAudioStreamReady` 校验 `category !in 1..3` 直接丢；`onAudioStateChange` 亦然。**宿主侧确实分了三类。**
- `core/.../sessioncore/HostAudioBridge.kt:47`：`queues=(1..3)`，每类一条 lane，互不阻塞；`attach()` 允许"合并已建立的类别"，并明确"附加 alternate 不得关闭 main"。
- `core/.../sessioncore/MainAudioOwnership.kt:88`：`Categories 1 and 3 send only while we hold main audio` —— **category 1 和 3 共用同一份 main audio 所有权**。
- `protocol-carplay/.../core/CarPlayAudioPlan.kt:155`：`bootstrapPlayback(...) = listOf(1).mapNotNull{...}` —— 预建**只有** category 1。
- `bridge/.../SessionController.kt:541`：866F 上 speech（category 3）**主动 SETUP 被代码显式抑制**；`:1062` 仍保留 `startSpeech` 入口，但走不到 SETUP。
- `protocol-carplay/.../core/AudioStreamLifecycle.kt`：lease 键是 `(type, purpose)`，`TEARDOWN` 只带 `type`，"一个 type 上未确认的 teardown 会毒化该 type 到重连"。

**也就是说：宿主给了 3 路，代码结构允许 3 路，但最后只有 1 路能过车机。** 这是现象，不是根因。

## 3. 根因（按依赖顺序，先修谁才谈得上分流）

### R1 会话必须先真正激活并活着 —— 这是第一前置，不是并行项

| 版本 | 第一条 | 第二条 | 结果 |
|---|---|---|---|
| v14.6 | media（未发）| `type100/alert`（cat 2）| 挂起 → `400` 与 RTSP `EOF` **同一毫秒**；`EOF = CONTROL_READY+7.5s` |
| v14.11 | `type102/media` SETUP **200**，AAC RTP 正常 | `speechRecognition`（cat 3，cseq=48）| 挂起 **2.011s** → `400` 与 `EOF` **同一毫秒**；`EOF` 提前到 `+2.97s` |

两次 `400` 都落在 **RTSP `EOF` 的同一毫秒**，而当时会话本就因激活超时在被拆。所以它们是**"拆链副产品"（解释 B）**，不是"车机拒绝第二条"（解释 A）。真 iPhone 在同车机上能三路分开调音量，已经把解释 A 排除。

**因此 v14.10（禁 alert）/ v14.11（只建 media）里的"866F 只允许一条"是误判**——那个结论是在"会话正在死"的条件下得出的。这两处代码应视为**临时护栏**，一旦激活稳定就该按 E0 复测并拆掉。

判定：**先修激活**（`CONTROL_READY+7.5s` EOF 的根因，v45 的常驻 WiAP 发布是新方向），否则任何多流实验都会重演"400 与 EOF 同刻"，再次被误读成"车机不让"。

### R2 路由映射错位：导航应走 alt（`type101/default`），我们先去撞 alert（`type100/alert`）

- 代码现状：`CarPlayAudioPlan.routeForCategory(2) → alert(100/alert)`，`selectPlayback` 顺序是 `listOf(alert, alternate)`，**alternate(101/default) 只是 400 之后的兜底**。
- 真 iPhone 的对应关系：**媒体 = main（type102/media）、导航提示 = alt（type101/default）、通话 = 蓝牙 HFP**。我们首选的那条，恰好不是它用的那条。
- 代价不对称：撞 `alert` 的 400 会**直接拖垮整条 RTSP**；`createAudioLocked` 里"400 后换 alternate 重试"的设计在会话已死时没有任何意义。
- 判定：**category 2 应把 `alternate(101/default)` 提到首选，`alert` 降级为例外**。这一条不需要等激活修好也能先验证（E3 单条试探）。

### R3 通话不是 CarPlay 流，是蓝牙 HFP —— 不要拿它当分流指标

866F 的日志里有 `retain Bluetooth`，代码里也有 `0x4e0b`（disabled Bluetooth）的整条探索史 —— 说明通话音频仍走**蓝牙链路**，方向盘上的"通话音量"调的是 HFP 那一路，不是 CarPlay 音频流。

所以"三路独立音量"要拆成两句话：
- **通话独立** → 证明蓝牙链路在，与 CarPlay 多流无关；
- **导航 vs 媒体能分开** → 这才证明 CarPlay **main + alt 并存**，是我们要复刻的东西。

别为了"通话分流"去建 `telephony` 流，那会把一条本来好好的 HFP 路径搞复杂。

### R4 main audio 单 owner：category 3 被当成"第二个 main"，天然与 media 互斥

`MainAudioOwnership` 的设计前提写得很直白：

> 发送 main audio 时如果车机也持有该流，会听到两条 main 重叠、电平跳动，而日志上看不出异常。

于是：

- `takeOwn()` 在 `THEIRS` 状态下**直接抛异常**，抑制新的 main SETUP；
- `allowsMainSend()` 只有 `OURS` 才放行；
- 866F 对 mid-session 的 release 公告**直接 RST**（`releaseOwnSilent()` 注释，`90(1) 2ca997d3/cf22ea8c`）。

问题在于**语义归类错了**：导航提示应该是 **alt**（独立流、独立 `audioType`、车机独立增益），却被归进 main owner 的管辖范围。分流要成立，必须让 **alt 不受 `MainAudioOwnership` 的单 owner 约束**（Siri/语音识别仍可留在 main 语义）。

### R5 生命周期 gate 以 type 为键，`TEARDOWN` 只带 type —— 不能热切换、不能只拆一路

`AudioStreamLifecycle.reserve(type, purpose, id)`：同一 `(type,purpose)` 只能有一个 lease；关闭走 `beginClose` → `TEARDOWN(streams=[{type}])`，**未确认就保留 tombstone，该 type 在本会话内不可再用**。

后果：
- 想"媒体走 type102、播报走 type101"要先拆一条再建一条，而 `TEARDOWN` 只带 type，等于把同 type 的所有用途一起拆；
- 一旦 teardown 没被确认（EOF 场景极常见），这个 type 直接废掉，只能重连；
- 所以**动态换路（分流→合流→再分流）在当前生命周期模型里不成立**，不是加个分支就行。

（media=102、alt=101 分属不同 type，这条对"并存"影响较小；对"要复用同 type 的两条 purpose"影响致命。）

### R6 宿主桥没有分流入口：只保留默认 PCM 路由，CarLife 的音频通道没接

- `VendorCastHost.selectCarLifePlusAudio()` 实现只有一行事件：`audio-route-default-pcm`。README 明确：**"不主动发送蓝牙音频路由请求"，"后续若接入音频路由协商，应根据已协商的通道和宿主回复实现"**。
- `CarVeX-本地劫持方案.md` 的"未做"清单里写着：**音频（9240/9241）仍走 CarVeX 自己的音频通道，没接 CarLife 的 PCM**。
- 也就是说：想让"导航播报走 CarWith 原生通道、媒体走 CarPlay"这种**跨链路分流**，桥里根本没接线；现在所有声音都从 CarLife 引擎的 PCM 出来，被 CarVeX 压进同一条 media 流。

### R7 证据缺口（现在最值钱的三条）

| 缺口 | 为什么关键 | 补齐成本 |
|---|---|---|
| 866F `/info` 的 `audioFormats` 原文 | 直接决定 `101/default` 有没有输出 mask。有 → 第二路有目标，R2 立刻可改；没有 → 只剩"跨链路"方案 | 低（日志已打 `INFO audio #N`，只是没留全文） |
| 真 iPhone 的 RTSP SETUP 原文 | 能直接抄：`type` / `audioType` / 建立顺序 / 是否并发 / 码率与 RED | 中（需 iPhone + 抓包） |
| 866F 是否经 iAP2 请求 alert/speech | 决定"按需建"这条路线是否存在 | 低（`RuntimeIap` 已能收，补日志即可） |

### R8 协议证据规则：混音/闪避不得宣称兼容

`carvex-carplay-research/.../airplay_audio_mic_channel`：

- `R-1.6`：**没有证据表明导航提示音走独立流、独立 raw 或与媒体混音** —— 不得假设。
- `R-5.4`：**拿到"媒体音+导航提示音同时存在"的抓包前，不得实现自动压低媒体音并声称符合车机预期；不得把提示音强行混进媒体流**。

所以"手机侧混音/闪避"只能写成**本端实验策略**；"把播报混进媒体流"连实验都要谨慎（会破坏 PT/时间戳统计）。

## 4. 为什么现在不能"改一行"

```
要分离的音频能各自调音量
  ├ 1) 会话活着（R1）                    ← 现在死在这
  ├ 2) 导航流建在 alt/101/default（R2）   ← 选错路由，一撞 400 就整条挂
  ├ 3) alt 不受 main 单 owner 约束（R4）   ← 模型要改
  └ 4) 并存/切换的生命周期支持（R5）        ← teardown 只带 type
```

顺序是**串行**的：1 不成立时，2/3/4 的实验结果都会被 EOF 污染（这正是 v14.10/v14.11 误判的成因）。所以最小可行动作不是"加 category 分支"，而是：

1. 先把激活做稳（E0 的前置）；
2. 拿到 `/info`（E2）确认 alt 有没有目标；
3. 用 E3 在**单条**条件下确认 `101/default` 能被 200 接受；
4. 再改 R2（路由序）→ R4（alt 脱离 main owner）→ R5（并存的生命周期）。

## 9. 通话为什么不上车机（走的是另一条路，与分流无关）

**真 iPhone 的通话不进 CarPlay 音频流，走蓝牙 HFP/SCO。** 无线 CarPlay 期间手机—车机的蓝牙链路是保持的（866F 日志 `retain Bluetooth`），车机作为 HF unit 收发通话音频；车机再用 iAP2 的 call state（`4154`/`4156`/`4158` 等）显示来电、用 HID/按键接挂。媒体和导航才走 Wi‑Fi 上的 RTP。

这就是"三个都能在方向盘上单独调音量"的真正原因：**通话是 SCO 那条物理链路，媒体/导航是 RTP 那条** —— 前者证明不了 CarPlay 多流，后者（导航 vs 媒体）才证明 main+alt。

**我们这条链路里，通话停在手机上是四件事叠加：**

1. **CarPlay 侧把电话能力声明成"没有"**：`PhoneSubscriptions.kt:7` 明写"本实现目前**没有通话状态来源**，所以这里只做'接受订阅 + 记录字段集'"；`Communications` 默认全 `false`（`telephonyEnabled=false`、`currentCallCount=0`、`initiateCallAvailable=false`）；`AirSession.kt:244` 对车机的 `0x4157` 直接回**空 `4158`**。车机据此认为这台手机没有电话能力 → 不建通话 UI、不发起通话音频。
2. **完全没有 SCO/HFP 路由代码**：全仓库搜不到 `startBluetoothSco` / `setCommunicationDevice` / `MODE_IN_COMMUNICATION` / `TelecomManager` / `InCallService`；`AndroidManifest` 里也没有任何通话或音频路由权限（只有蓝牙、网络、通知一类）。**通话音频由系统电话 App 与 Telecom 决定，CarVeX 插不上手。**
3. **宿主桥只覆盖 PCM 1..3 + 麦克风回收**：`ISystemAudioCallback`（category 1..3）与 `IRemoteAudioListener`（mic）里没有通话；`selectCarLifePlusAudio()` 只有一句 `audio-route-default-pcm`，从不发起蓝牙音频路由请求。
4. **通话键只是转发**：`MixingKeys.kt:62` 把 `ui:mobilephone:` 映射到宿主 `PHONE` 键，等于交给 CarWith 的手机端拨号 UI 处理，声音仍在手机本地。

**要让通话也上车机，三条路径与门槛：**

| 路径 | 做法 | 门槛 |
|---|---|---|
| A HFP/SCO（最接近真 iPhone） | 手机与 866F 的 BT 保持、车机作 HF；通话时把 communication device 切到 `BT_SCO` | 需默认拨号器 / `InCallService` / 系统签名或特权（`MODIFY_AUDIO_SETTINGS` + Telecom 的音频路由）；**普通 App 做不到**，只能靠 Shizuku/root、系统蓝牙设置里"通话音频"托管，或让 CarWith 自己负责电话 |
| B CarPlay telephony 流（`type100/audioType=telephony`） | 先声明 telephony 能力 + 真实通话状态（TelecomManager），再把通话 PCM 压进 RTP | 通话录音需要 `VOICE_CALL` / `CAPTURE_AUDIO_OUTPUT` 级别权限；866F 是否接受这条流**完全未验证** |
| C 现状 | 只在车机上接/挂（HID 键已通），声音留手机 | 无 |

**对分流结论的影响**：通话不参与 main+alt 的分流问题——它在另一条物理链路上。所以分流只需做 **media(`102`) + 导航 alt(`101/default`)**，别为了"通话也分流"去建 `telephony` 流，那会把一条本来能用的 HFP 路径搞复杂。
